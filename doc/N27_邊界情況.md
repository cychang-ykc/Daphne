# N27 各平台的邊界情況

使用者或其他程式做了「正常播放以外」的事時，Daphne（與 MIKU 外殼）在各平台上的行為。設計與實作細節在 N4（播放整合）、N24（輸出 API）；這裡只記「發生什麼事」。

「依據」欄：**實測**＝在實機上量過或看過；**程式**＝從程式碼判斷，還沒在實機上確認；**未驗證**＝還不知道。之後實測過的項目請改成「實測」並寫上日期或對應的文件。

## 所有平台（播放核心）

| 情境 | 行為 | 依據 |
|---|---|---|
| 有升頻濾波器時開始播放、跳轉、重開裝置 | 開頭丟掉濾波器的延遲，第一個聽到的就是音樂；結尾送零到最後一個樣本播出為止，之後的餘振不播。輸出長度等於原曲 × 倍率（N26「只播放音樂，不播濾波器延遲」） | 實測（2026-10-16，Windows 測試、Mac CLI 1M taps） |
| 跳轉 | 鏈先清空：跳轉點之後約半個濾波器長度的輸出只用到跳轉點之後的樣本（濾波器前面的歷史是零）。大 taps 下若聽到喀聲，可加短淡入（N26 待觀察） | 程式 |
| 一首快播完時（最後約 0.5 秒，解碼器已經在解無縫播放的下一首）往回跳轉 | 跳轉在這一首：重新開啟這一首，從跳轉點播起。修正前會先清空環再判斷「下一首聽到了沒」，清空後已寫入的都算聽到，跳轉落在下一首的同一個位置 | 實測（單元測試） |
| 同上，但這一首重新開不了（檔案被移走、外接硬碟拔掉） | 播放失敗（`failed`，錯誤「seek: the track could not be opened again」）。修正前會用下一首的解碼器繼續，在這個位置播出下一首 | 實測（單元測試） |
| 外接硬碟播放中停止回應幾秒（USB 硬碟休眠後重新轉起來） | 預讀（N2）在背景把檔案讀在播放位置前方，視窗 64 MiB（16-bit / 44.1 kHz WAV 約 6 分鐘、24-bit / 192 kHz 約 1 分鐘），停頓比這短就聽不到。視窗讀完了磁碟還沒回應才會斷音；log 記下慢的磁碟讀取（「read ahead: a disk read of … took … ms」）與播放迴圈慢的那一圈。修正前解碼器在處理執行緒上讀檔，停頓超過環的 0.5 秒就斷音 | 實測（現象，PR #54 作者回報）；修正以單元測試驗證（假的慢磁碟、經播放器） |
| 很大的檔（超過 1 GiB 的 24-bit / 192 kHz WAV 等） | 一樣預讀，記憶體固定 64 MiB；seek 到遠處只等那裡的一次磁碟讀取 | 實測（單元測試，3 GiB 稀疏檔；Linux 上 126 MB WAV 的解碼結果與 main 相同） |
| 播放中檔案被截短或刪除 | 截短：讀到新的檔尾就當成結束，不會卡住。刪除：已經開著的檔照常讀完（Windows 以共享刪除開檔） | 實測（單元測試，截短）；刪除為程式 |
| 無縫播放的下一首開不了 | 不做無縫，這一首播完；原因寫進 log（事件「the next track could not be opened (…)」） | 實測（單元測試） |
| 無縫播放，下一首取樣率不同 | 只有輸出取樣率相同（例如都升到同一個取樣率）才無縫接上；否則這一首結束，由主程式載入下一首 | 程式（N4） |
| 裝置拒絕要求的取樣率 / DSD 傳輸 | 依序降級（PCM：取樣率減半；DSD：原生 → DoP → 較低倍率），每次中間的失敗都寫進 log：「the output at … failed (原因): trying …」 | 實測（假裝置的單元測試） |
| 播放中改設定（apply）後立刻 stop | stop 要等那次重開先把排隊的聲音放完、淡出，再關裝置；Mac 上一般 stop 0.84 s，這種情況約 1.7 s。結果正確 | 實測（2026-10-16，Mac + USB DAC） |
| 損毀或刻意構造的 DSD 檔（DSF / DFF 標頭的值不合理） | 載入失敗並回報是哪個值（`dc_load` 回傳 `DC_ERR_FILE`）；下載中斷而資料不完整的檔案播放存在的部分（N3） | 實測（單元測試） |
| 損毀的 PCM 檔，標頭的值不合理（例如 FLAC 的 STREAMINFO 寫取樣率 0） | **目前整個程序結束**：解碼器照樣開啟（取樣率 0），播放器計算取樣率倍數時整數除以零（SIGFPE），例外處理攔不到；當成無縫的下一首時，在背景預備執行緒上同樣發生，正在播的這首也一起結束（N26「已知問題」） | 實測（2026-10-25，單元測試重現） |
| 解碼、建立處理鏈或開檔時拋出例外（記憶體不足、函式庫錯誤） | 開始前：載入失敗，錯誤是「internal error: …」。播放中：與裝置失敗相同，停止裝置並送 `failed` 事件。背景重建：保留目前的處理鏈。無縫播放的下一首：不做無縫，這一首照常播完。程序都不會結束（修正前從處理執行緒拋出的例外會讓 MIKU 閃退） | 實測（單元測試，假裝置） |
| 第一次設計長濾波器時停止、換歌或關閉主程式 | 設計在一個區塊內停下（每個設計執行緒都檢查），被取消的載入回傳 `DC_ERR_CANCELLED`，什麼都不播、不顯示錯誤；被跳過的歌不會依序設計完。在驅動裡卡住的裝置開啟中斷不了，要等它結束（N4「C API 的執行緒」） | 實測（2026-10-22，Windows MIKU、Mac helper，N26） |
| 取消剛好落在裝置啟動的那一刻 | 裝置先開始，`dc_load` 再停止它並回傳 `DC_ERR_CANCELLED`：可能漏出幾 ms 的聲音，事件佇列與報告留著那首的 `started`，主程式會短暫顯示那一首的播放路徑（N26「已知問題」） | 實測（單元測試，啟動加了 300 ms 延遲的假裝置） |
| 播放中拔除裝置 | 輸出回報失敗（`failed`），播放器停止並送 `failed` 事件，主程式決定接下來怎麼做 | macOS 實測（2026-10-16，USB DAC，MIKU 獨佔）；Windows 程式 |

## Windows（WASAPI 獨佔 / 共享、ASIO）

| 情境 | 行為 | 依據 |
|---|---|---|
| MIKU（Daphne）以 WASAPI 獨佔播放並**暫停**，再到 Windows 音訊設定把同一台 DAC 設成預設輸出、用瀏覽器播 YouTube | 暫停不放掉裝置：WASAPI 獨佔串流照常運轉、送靜音（按播放可立刻續播）。瀏覽器走共享模式，裝置被獨佔時 Windows 拒絕它（裝置使用中），YouTube 通常會沒有聲音或音訊卡住（依瀏覽器而定）；MIKU 不受影響。MIKU 停止或結束後裝置才放出來，瀏覽器可能要暫停再播放、或重新整理頁面才恢復聲音。Windows 版 MIKU 與 Daphne 的 Windows 擴充都沒有「讓出裝置」的規則（Mac 版有，見下） | 程式；實機未驗證 |
| Windows「優先使用獨佔模式應用程式」 | 只決定獨佔程式能不能搶走正在使用的裝置；共享模式的程式不能反過來搶獨佔中的裝置 | 程式（Windows 的設計） |
| 換曲（下一首不能無縫接上） | 關閉再重開輸出。WASAPI 獨佔與 ASIO 關閉時不還原任何設定，重開時直接用新格式：只有重開那一下，沒有 Mac 那種兩次重新鎖定，也不搬系統輸出。沒有保留裝置的機制（N24「保留裝置」只做 macOS） | 程式 |
| 播放中改 Windows 的預設輸出裝置 | Daphne 的輸出不監聽預設裝置改變，繼續在原本開啟的裝置上播放；要不要搬到新裝置由主程式決定 | 程式 |
| WASAPI 裝置失效（拔除、停用、格式被改） | 輸出回報失敗（「Exclusive / Shared Device Invalidated」），見上「播放中拔除裝置」 | 程式 |
| ASIO 驅動要求重設（取樣率被改、驅動重設） | 播放器在原位置重開裝置 | 程式（N24） |
| WASAPI 共享模式 | 不是 bit-perfect，回報原因「shared mode (system mixer)」；取樣率與裝置不同時由 Windows 轉換（`AUTOCONVERTPCM`），原因改成「the system resamples to the device's N Hz」，報告的 `system_rate` 是混音器的取樣率，MIKU 的訊號路徑顯示它（「系統轉換」一列） | 實測（N24、N26）；`system_rate` 為程式 |
| WASAPI 共享模式播 DSD 檔（`output.dsd = auto`） | 不試 DoP，直接轉成 PCM（混音器的取樣率能整除 DSD 取樣率時轉成它）。修正前會先試 DoP：共享輸出接受任何取樣率，DoP 的檢查因此通過，DoP 資料被混音器當成 PCM 轉換，聽起來是雜音，報告還寫 bit-perfect | 程式；以假裝置的單元測試驗證 |
| MIKU 播 YouTube Music（即時輸入）時重新載入頁面、或 MIKU 換掉共用的環 | 卸離期間讀到靜音；超過 20 ms 算一次斷流，抖動緩衝的目標加 50 ms（最多 0.3 s，程式執行期間保留）。換上的新環從舊環的讀取位置讀起，新環的寫入位置要從 0 開始（N2） | 程式 |
| MIKU 播 DSD 檔時改「DSD 播放方式」或「DAC 最高 DSD」 | 停止並在原位置重新載入（`ReconfigureAsync`） | 程式 |

## macOS（Core Audio 獨佔 = hog mode / 共享）

| 情境 | 行為 | 依據 |
|---|---|---|
| 獨佔播放時的「系統輸出」 | Daphne 佔住 DAC 時，macOS 把系統輸出移到另一台裝置（例如內建輸出；只有一台裝置時就沒有系統輸出），放掉後 1–3 s 才移回。聲音照常送到 DAC。系統的其他聲音（通知等）這段時間從另一台裝置出聲 | 實測（2026-10-15，USB DAC） |
| 停止後馬上查詢系統輸出（外殼的 `probeDevice(null)`） | 頭 1–3 s 讀到的是內建輸出（上一項的副作用）；只影響顯示，停止後馬上播下一首仍送到 DAC（core 記得剛放掉的裝置）。暫緩處理（N26） | 實測 |
| 換曲（同一台裝置、獨佔，經 helper / MIKU） | 裝置保留著（hog、取樣率、DAC 格式，送靜音），下一首直接接手：同取樣率完全不動（96 k 接 96 k 換曲 30 ms），不同取樣率只重新鎖定一次；系統輸出不會移走再移回。CLI 不保留：96 k 接 96 k 要還原 44.1 kHz 再設回 96 kHz，約 1.7 s | 實測（2026-10-16，USB DAC） |
| 播完最後一首、或 MIKU 暫停 / 停止（獨佔） | 裝置保留著，其他程式不能用這台 DAC。何時放開由 MIKU 決定：MIKU 不在前景且沒在播放時約 4 s 後、改播 YouTube、或結束程式，才還原取樣率與 DAC 格式並放掉 hog | 實測（保留與放開）；放開的時機依 MIKU 的程式（`main.js`） |
| MIKU 當掉（helper 還在跑） | helper 的 stdin 讀到結尾，照理走 `quit` 的清理（停止、還原取樣率與 DAC 格式、放掉 hog）；但 helper 沒有忽略 `SIGPIPE`，清理期間只要再寫一行到已關閉的 stdout（事件、設計進度），就被系統結束，取樣率與 DAC 格式不還原（N26「已知問題」） | 程式；`SIGPIPE` 結束以 Linux 上的 helper 確認（結束碼 141） |
| helper 程序當掉（保留著裝置時） | 系統跟著程序放掉 hog，但 DAC 的取樣率停在最後的值，不會還原（與 MIKU 自己的輸出相同）。外殼會重新啟動 helper 並從原位置繼續（一分鐘最多 3 次） | 程式 |
| 其他程式改 DAC 的取樣率（例如「音訊 MIDI 設定」） | 獨佔：macOS 拒絕其他程序的變更（`'!hog'`），照常 bit-perfect 播完。共享：在原位置以新的取樣率重開，播到結尾 | 實測（2026-10-15） |
| 裝置被其他程序 hog 住 | 獨佔與共享都開不了，不會卡住。獨佔（或以系統輸出開啟而系統輸出不存在）回報「… is in exclusive use by another application (pid N)」；共享模式指定裝置時不檢查 hog，要到啟動 IO 才失敗，訊息不同 | 實測（獨佔，N24）；共享的訊息為程式 |
| 共享模式，裝置取樣率不是要求值的整數倍（48 k 檔、44.1 kHz 的裝置） | 由 Core Audio 的 `AudioConverter` 在 IO 回呼裡轉換（與 WASAPI 共享相同）；整數倍時由 Daphne 自己的升頻濾波器做 | 實測（2026-10-15） |
| DSD | macOS 沒有原生 DSD API，只走 DoP（獨佔）；共享模式不試 DoP，直接轉成 PCM（修正前會先試 DoP，由 `AudioConverter` 轉換，結果是雜音）。DoP 從不經過轉換器。DAC 宣稱的最高倍率不一定可靠（測試用的 USB DAC 只到 DSD128） | 實測（獨佔 DoP）；共享為程式（假裝置的單元測試） |
| 獨佔，DAC 沒有這首歌的取樣率家族（只有 48 kHz 的 HDMI 或虛擬裝置播 44.1 kHz；最高 96 kHz 的 DAC 播 192 kHz） | 先照常試裝置自己的取樣率；鏈用不了時最後由 Core Audio 的 `AudioConverter` 轉成裝置的取樣率播放（log「trying 44100 Hz (resampled by the system)」），報告不是 bit-perfect（「the system resamples to the device's 48000 Hz」），MIKU 顯示實際的 48 kHz。修正前整首播不出來（「not an integer multiple」）。同家族往下（DAC 只到 352.8 kHz）仍由 Daphne 升頻，不轉換 | 現象：MIKU 的 Mac 穩定性測試（#53 作者回報）；修正以假裝置的單元測試驗證，Core Audio 的轉換未在實機確認 |
| 5.1 檔在立體聲裝置上 | 以立體聲開啟，由處理鏈降混。修正前開啟失敗（「has 2 output channels, the stream 6」） | 現象：#53 作者回報；修正為程式 |
| MIKU 播 DSD 檔時改「DSD 播放方式」或「DAC 最高 DSD」 | 在原位置重新載入（`engine.js` 的 `applyOutput`）。載入還沒完成時又改一次，第二次的變更會被忽略，繼續用第一次的設定播放，直到下一首（N26「已知問題」） | 程式 |
| DSD，DAC 鎖不到 DoP 的取樣率（例如剛接回去的 USB DAC 要 176.4 kHz 卻停在 88.2 kHz，或最高只到 96 kHz 的 DAC） | 轉成 PCM；鎖定的取樣率低於平常的 176.4 / 192 kHz 而且能整除 DSD 取樣率時，直接轉成那個取樣率（log「converting at … Hz, the rate the device locked」），DAC 那邊的原因也寫進 log。拔插後停在 88.2 kHz 的原因不明，之後沒有重現 | 實測（現象，2026-10-16）；修正以單元測試驗證 |
| Mac 進入閒置睡眠（例如從 ssh 操作、沒有人登入） | dark wake 時任何裝置都沒有音訊 IO（回呼數為 0），播放會卡住。測試機已設定永不睡眠（`pmset -a sleep 0`） | 實測（2026-10-16） |
| 播放中拔掉 USB DAC（獨佔，MIKU） | MIKU 的進度再走幾秒，接著顯示「the output device was removed」，不會卡住。Daphne 收到 macOS 的通知（`DeviceIsAlive` 變成 0）後幾 ms 內就停止；那幾秒應該是 macOS 從拔除到發通知的時間 | 實測（2026-10-16）；延遲的原因從程式判斷 |
| 錄音（例如錄 BlackHole 驗證 bit-perfect）的程序沒有麥克風權限 | macOS 10.14 起錄任何輸入裝置都要麥克風權限；沒有權限時不會報錯，只會收到全零。從 ssh 執行、沒有人在桌面上授權過時就是這樣。在桌面上給「終端機」麥克風權限之後，從 ssh 執行的同一個測試程式也錄得到 | 實測（2026-10-16） |
| hog 住、停止中的裝置被改取樣率後再放掉 hog | 這個程序之後無法在它上面開始 IO（`AudioDeviceStart` 卡住數秒，MIKU 遇過）。所以 Daphne 只在 IO 運轉中改取樣率與格式（N24） | 程式（MIKU 的經驗） |

## Linux

| 情境 | 行為 | 依據 |
|---|---|---|
| 輸出 | ALSA 輸出還沒做（N26 暫緩），目前 Linux 版只有解碼、DSP 與測試，沒有實體裝置輸出 | 程式 |
| 即時排程 | 處理執行緒拿到 `SCHED_FIFO` 時，它建立的濾波器設計與無縫換軌預備執行緒回到 `SCHED_OTHER`；替它工作的 double-double `WorkerPool` worker 則跟著進入 `SCHED_FIFO`（`RealtimeHelperScope`）。都還沒在有即時權限的 Linux 上確認，兩核心機器會不會被 FIFO 的 worker 佔滿也未知（N26） | 未驗證 |
