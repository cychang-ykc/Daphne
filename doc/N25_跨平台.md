# N25 跨平台

`platform/`、`core/include/daphne/engine/player.h`（`PlayerDeps`）、`core/src/output_win.cpp`、`core/src/output_mac.cpp`、`core/src/output_none.cpp`、`helper/`、`miku/`、`scripts/build_for_miku.ps1`、`tests/fake_output.h`、`tests/test_player.cpp`、`.github/workflows/build.yml`、`.github/workflows/sanitizers.yml`、`fuzz/`

引擎、處理鏈與播放器是一般的 C++20；作業系統相關的部分集中在 `platform/` 與裝置輸出。Windows、macOS、Linux 都能建置並執行全部單元測試（除 CI 外，也在 macOS 11 與 Debian 12 實機上驗證，見「驗證」）。Windows（WASAPI / ASIO）與 macOS（Core Audio，N24）有實際的裝置輸出；Linux（ALSA）是後續步驟（見「player.cpp 拆分計畫」與 N26）。

## 分層

```
host（Windows MIKU 擴充：P/Invoke｜macOS MIKU 外殼：daphne-helper｜CLI）
   │  C API（dc_*）
Player ── DspChain、解碼器、DSD 封裝（可攜）
   │  PlayerDeps：裝置輸出、PCM 解碼器
   ├── 裝置輸出（AudioOutput）：Windows：WASAPI、ASIO｜macOS：Core Audio｜測試：FakeOutput
   └── platform/：執行緒排程、浮點控制、環境變數、快取資料夾、開檔
```

依賴只往下走：播放器不知道自己在哪個作業系統上，也不知道裝置是哪一種。

## platform 層（`daphne_platform`）

| 項目 | Windows | macOS | Linux |
|---|---|---|---|
| `RealtimeScope`（處理執行緒） | MMCSS「Audio」、1 ms 計時器解析度、關閉 EcoQoS 節流（與先前相同） | time-constraint policy（每 10 ms 最多 5 ms） | `SCHED_FIFO`（範圍下三分之一；沒有權限時維持原狀） |
| `RealtimeHelperScope`（調變器右聲道；替即時執行緒工作的 `WorkerPool` worker） | MMCSS「Audio」 | 同上 | 同上 |
| 執行緒優先權（背景 / 低於一般 / 一般 / 高於一般） | `THREAD_MODE_BACKGROUND_BEGIN` 與對應的 `THREAD_PRIORITY_*` | QoS：background / utility / default / user-initiated | `SCHED_IDLE`；其他為 `SCHED_OTHER` 加 nice（5 / 0 / −5） |
| FTZ / DAZ | MXCSR（x86）；FPCR.FZ（ARM64，`_ReadStatusReg` / `_WriteStatusReg`） | FPCR.FZ（Apple Silicon）；MXCSR（Intel） | MXCSR 或 FPCR |
| 使用者快取資料夾 | `%LOCALAPPDATA%` | `~/Library/Caches` | `$XDG_CACHE_HOME`，否則 `~/.cache` |
| 開檔、64 位元 seek | `_wfopen_s`、`_fseeki64` | `fopen`、`fseeko` | 同 macOS |

- 排程是盡力而為：作業系統拒絕時執行緒維持原狀，不會失敗（`RealtimeScope::realtime()` 回報是否成功）。
- 濾波器快取：`<使用者快取>/daphne/filters`，`DAPHNE_FILTER_CACHE` 在三個平台都照舊可用。
- `parallel_for` 的 worker 沿用建立者的優先權：Windows 讀實際值並歸到三級（低於一般 / 一般 / 高於一般；原本照抄確切值），其他平台記錄在 thread_local（只有經由這一層設定的值）。
- Linux 的新執行緒繼承建立者的排程策略（`PTHREAD_INHERIT_SCHED`）：處理執行緒拿到 `SCHED_FIFO` 時，由它建立的濾波器設計、`parallel_for` 的 worker、無縫換軌預備原本也是 `SCHED_FIFO`，而 nice 對它們無效，長濾波器的設計會以即時優先權佔滿所有核心。`set_thread_priority()` 設一般類的優先權時，先把 `SCHED_OTHER` 以外的策略（FIFO、RR、IDLE）切回 `SCHED_OTHER`（降低一律允許），再設 nice。Windows 的 MMCSS 與 macOS 的 time-constraint policy 不會被繼承。
- double-double 重新取樣的 `WorkerPool` worker 平常是「高於一般」；替即時執行緒（`RealtimeScope` 之內，`in_realtime_scope()`）工作時進入 `RealtimeHelperScope`（Windows MMCSS "Audio"、macOS time-constraint、Linux `SCHED_FIFO`），處理執行緒每個 block 都要等它們。只在呼叫者的類別改變時切換（背景預熱的鏈換上之後），不是每個 block。

## 路徑

- 引擎一律用 `std::filesystem::path`（`Decoder::open`、`open_decoder`、`DsdFile`、`Player`、`filter_cache_dir`）。Windows 上是原生 UTF-16，其他平台是 UTF-8。
- 副檔名判斷統一用 `file_extension()`（最後一個 `.` 之後、ASCII 小寫），取代原本兩份相同的程式碼。
- dr_wav / dr_flac / minimp3 在 Windows 用 `_w` 版本，其他平台用 `char` 版本；FFmpeg 收 UTF-8。這是預讀（`FileBytes`，N2）開不了時的退路；預讀自己開檔：Windows 用 `CreateFileW`（共享讀、寫、刪除，播放中的檔案可改名或刪除），其他平台用 `platform::open_file` 與 64-bit 的 `seek_file`。
- 路徑與 UTF-8 的轉換（`platform::path_to_utf8` / `path_from_utf8`）不會丟例外：Windows 用 `WideCharToMultiByte` / `MultiByteToWideChar`，無效的序列換成 U+FFFD；其他平台路徑本來就是位元組，原樣通過。`std::filesystem` 自己的轉換（`u8string()`、`char8_t` 建構子）在 MSVC 遇到無效序列會丟例外，而 NTFS 允許含孤立 surrogate 的檔名；處理執行緒一開始就判斷副檔名，例外會變成 `std::terminate`，主程式（MIKU）隨之結束。

## 裝置輸出

- `Player` 從 `PlayerDeps` 取得裝置（`OutputOpener`）、PCM 解碼器（`DecoderOpener`）與輸出的能力（`OutputCapsQuery`，N24）；沒給時用 `platform_output_opener()`、`open_decoder` 與 `platform_output_caps()`。
  - `output_win.cpp`：WASAPI 獨占 / 共享、ASIO，建立方式與先前相同。
  - `output_mac.cpp`（macOS）：Core Audio 獨佔 / 共享（`coreaudio_output.cpp`、`devices_coreaudio.cpp`，連結 CoreAudio 與 CoreFoundation framework）。
  - `output_none.cpp`（Linux）：目前沒有裝置，開啟時回報原因；裝置列表為空。
- 原本對 `AsioOutput` / `WasapiOutput` 的 `dynamic_cast` 改成 `AudioOutput` 的虛擬函式（N24）：`probe_before_design()`、`supported_rates()`、`buffer_fallback()`。
- 開啟裝置之前就要決定的事由各平台的輸出後端回答（`OutputCaps`，`platform_output_caps()`），播放器不認得 API 名稱：有沒有原生 DSD（ASIO）、是不是共享混音（WASAPI 共享、Core Audio 共享）、`output.buffer_ms` 是否設定緩衝（ASIO 不是：用驅動自己的設定）。

## dsp

- AVX2 的 double-double 核心只用於 x86（N8）；其他 CPU（Apple Silicon、ARM64 Linux）走 scalar 路徑，運算順序相同，結果逐位元相同。
  - 依「編譯目標」決定，不看建置主機：`dd_conv.h` 由編譯器的預先定義巨集決定 `DAPHNE_DD_AVX2`（x86，排除定義了 `_M_X64` 但沒有 AVX2 的 ARM64EC）；`dd_conv_avx2.cpp` 一律加入編譯，非 x86 時是空的。
  - 編譯旗標只給 x86：MSVC 依 `CMAKE_CXX_COMPILER_ARCHITECTURE_ID`（x64 / x86）給 `/arch:AVX2`；Apple 依 `CMAKE_OSX_ARCHITECTURES`，universal 建置只對 x86_64 部分給 `-Xarch_x86_64 -mavx2 -mfma`；其他依 `CMAKE_SYSTEM_PROCESSOR` 給 `-mavx2 -mfma`。原本一律看 `CMAKE_SYSTEM_PROCESSOR`（建置主機的 CPU），Intel Mac 上的 universal 建置與 x64 主機上的 VS `-A ARM64` 建置都會失敗。
  - GCC / Clang 以 `__builtin_cpu_supports` 偵測 AVX2 + FMA；MSVC 的 cpuid 只在 x86 編譯。
- 沒有 FMA 指令的 CPU（Intel Haswell 以前、AMD Piledriver 以前）：double-double 的乘法改用 FMA 的精確模擬，結果與硬體 FMA 逐位元相同（`dsp/include/daphne/dsp/fma.h`，N8）。原本 C 函式庫以軟體計算 `std::fma`，慢約 100 倍：i5-3210M 上 1024 點中間相位設計要 3.0 s（現在 0.44 s）。
- GCC / Clang 一律 `-ffp-contract=off`：編譯器不自行把 `a * b + c` 合成 FMA（Clang 在 ARM64 預設會這樣做）。double-double 的每一步與 FMA 模擬都需要照寫的方式逐次捨入；MSVC 預設的 `/fp:precise` 不會合成。

## C API（決定紀錄）

- 原本收 `wchar_t*` 路徑的函式全部保留，行為不變，MIKU 的 C# 擴充不用改。
- 新增 UTF-8 版本：`dc_load_utf8`、`dc_set_next_utf8`、`dc_set_next_gain_utf8`、`dc_filter_cache_dir_utf8`。新的 host（macOS、Linux）建議用這些。
- `dc_abi_version()` 由 1 改為 2（只有新增）；之後 3 加上保留裝置（`dc_keep_device` 等，macOS），4 加上 `dc_cancel` 與會取消載入中的 `dc_stop`（N4「C API 的執行緒」）。
- 其他平台的 `wchar_t` 是 UTF-32：`wchar_t` 版本在那裡仍可用，內部轉成 UTF-8。
- 共享庫只匯出 `dc_*`（`daphne_core.dll` / `libdaphne_core.so` / `libdaphne_core.dylib`）。

## CLI

- 參數一律是 UTF-8：Windows 的 `wmain` 先把 UTF-16 轉成 UTF-8，其他平台直接用 `main`；路徑在交給引擎或開檔時才轉成 `std::filesystem::path`。
- `decode-test --md5` 改用內建的 MD5（RFC 1321），不再依賴 BCrypt。
- Ctrl+C：Windows 用 console handler，其他平台用 `SIGINT` / `SIGTERM`。

## 建置

```
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --config Release --parallel
ctest --test-dir build -C Release --output-on-failure
```

- Windows 照舊可用 `scripts\build.cmd`。
- 靜態庫一律編成 position-independent，才能放進共享的 `daphne_core`；符號預設隱藏。
- FFmpeg：CMake 快取變數 `DAPHNE_FFMPEG_DIR`（預設 `third_party/ffmpeg`）。Windows 一律用它（`scripts/fetch_ffmpeg.ps1` 從本 repository 的 release 下載，檢查 SHA-256）；macOS / Linux 先看它，沒有時用 pkg-config 找已安裝的開發套件（`pack-mac.sh` 為每個架構各編一份並傳入）。
- ASIO SDK 只在 Windows 使用。
- MSVC 專用的 `#pragma warning` 只在 MSVC 生效。
- 非 Windows 的 `platform` 以 `_FILE_OFFSET_BITS=64` 編譯（32-bit Linux 的 `off_t` 才是 64 位元，DSD 檔超過 2 GB 時 seek 才正確），並以 `static_assert` 確認。
- 工具鏈：CMake 3.25 以上。驗證過的編譯器：MSVC 2022、Apple clang 12.0.5（macOS 11 的最新版）與 CI 的 Xcode 15、GCC 13（CI）與 15.3。要支援舊版 Apple clang，lambda 不能捕捉 structured binding（clang 16，即 Apple clang 15 起才支援）。
- 警告：專案自己的 target 以 `daphne_warnings()` 開警告：MSVC `/W4`，GCC / Clang `-Wall -Wextra`（第三方程式碼不開：catch2 另有設定，vendored 標頭是 system include）。`-DDAPHNE_WARNINGS_AS_ERRORS=ON` 時警告視為錯誤（`/WX`、`-Werror`），CI 以此建置。
- CI（`.github/workflows/build.yml`）：Windows（MSVC）、Linux（GCC）、Linux 加系統 FFmpeg（Ubuntu 套件，pkg-config）、macOS 14（Apple Silicon、Clang），每個 PR 與推到 `main`、`cross-platform-plan`（已合併，觸發條件還在）時建置並跑全部單元測試，警告視為錯誤；其他分支用 `workflow_dispatch` 手動執行。CI 不裝 ASIO SDK（只在 Windows 本機建置）。
- Sanitizer 與 fuzz（`.github/workflows/sanitizers.yml`，Linux、Clang，每個 PR 與推到 `main`）：
  - `asan`：AddressSanitizer + UndefinedBehaviorSanitizer，全部單元測試。`tsan`：ThreadSanitizer，播放器、C API、即時輸入的測試（`[player],[capi],[live]`）。CMake 的 `-DDAPHNE_SANITIZE=address,undefined`（或 `thread`）套用到所有 target，不 recover：一有發現就結束，測試失敗。
  - `fuzz`：libFuzzer（`-DDAPHNE_BUILD_FUZZ=ON`，`fuzz/`）：`fuzz_dsd`（DsdFile）與 `fuzz_decoder`（dr_wav / dr_flac / minimp3，第一個位元組選類型），每個 60 秒，從 `fuzz/corpus/` 的種子開始（`fuzz/make_seeds.py`）；觸發問題的輸入留成 artifact，修好後放進 corpus 當回歸種子。
  - 第一次執行找到的：即時輸入的寫入索引以 `volatile` 讀取（TSan：資料競爭；改成 acquire 原子讀取）、dr_flac 跳轉估算把 inf / NaN 轉成整數（UBSan；本地修補，README）。

- `.gitattributes` 讓 `*.sh` 在每個 checkout 都是 LF（Windows checkout 的 CRLF 腳本拿到 Mac 會在 `set -o pipefail` 失敗）。
- 兩邊的打包都還沒有放 nlohmann/json 的 MIT 授權，Windows 也沒有放 Daphne 與 FFmpeg 的授權檔（N26「已知問題」）。
- 打包不在 CI 裡執行：`pack-mac.sh` 的 arm64 部分只在 Intel Mac 上建置過，沒有在 Apple Silicon 上執行（N26「尚未驗證」）。

## 播放器測試（`tests/test_player.cpp`）

`FakeOutput` 經由與 WASAPI / ASIO 相同的 `RingFeeder` 讀環。每次先等到有一整個緩衝的資料（最多 200 ms）才取，所以全速執行也不會 underrun，收到的就是播放器寫出的每一個樣本。來源由 `MemoryDecoder` 提供合成訊號。

| 測試 | 檢查 |
|---|---|
| 原取樣率、24-bit | bit-perfect：每個樣本與來源相同，之後全為 0；報告為 bit-perfect、沒有處理級 |
| `2x`、`auto` 升頻 | 裝置取樣率 88.2 / 705.6 kHz；長度 = 來源 × 倍率（加濾波器尾巴）；1 kHz 正弦量得 1000 ± 0.5 Hz |
| 裝置拒絕取樣率 | 依序嘗試 705.6k → 352.8k → 176.4k，以 176.4 kHz 播放，頻率正確 |
| 同取樣率無縫 | 兩軌接起來逐樣本相同，換軌回報一次 |
| 不同取樣率無縫（固定 176.4 kHz 輸出） | 經新的處理鏈接起來，裝置只開一次，接點沒有空白，第二軌頻率正確 |
| 搜尋 | 淡入之後從目標 frame 起逐樣本相同，直到結尾 |
| 暫停 | 暫停中位置不動；繼續後結尾逐樣本相同 |
| 音量 | 就地套用，裝置不重開，之後的振幅為一半 |
| 換濾波器 | 背景重建並交叉淡化，裝置不重開，長度不變、沒有空白 |
| 換輸出取樣率 | 裝置重開（44.1 → 88.2 kHz），兩段合起來涵蓋整軌一次；重開前最後一個 chunk（4096 個來源 frame：20 ms 淡出，之後為 0）在重開後從頭再播一次 |
| 驅動要求重設 | 裝置重開並從原位置繼續 |
| 即時輸入（來源取樣率與升頻到 192 kHz） | 預填與 0.15 s 抖動緩衝的靜音之後，是生產端的 1 kHz 正弦、沒有空白；播放器這一側（解碼器已讀、裝置還沒播放）不超過 0.12 s（實測約 0.06 s，改之前 0.77 s） |
| DSF 直送（DoP） | DoP 標記從前導靜音到結尾不間斷交替，音樂 frame 數正確 |
| dsd 核心（DoP） | 標記不間斷交替，長度正確 |

- `DAPHNE_PLAYER_DUMP=<資料夾>`：與時間無關的 8 個測試把裝置收到的位元組寫成 `<名稱>.bin`。重構前後各跑一次、逐位元組比較，就能確認行為沒有改變。
- 雜訊來源用 `mt19937` 的原始輸出（標準規定的數列）。`uniform_int_distribution` 的演算法由各家標準函式庫自訂（MSVC STL 與 libc++ 結果不同），原本兩個平台的來源就不一樣，golden 檔無法跨平台比對。
- 跨平台比對 golden 檔（Windows MSVC 與 macOS Apple clang）：`bitperfect`、`gapless_same`、`dsf_dop` 逐位元組相同；來源是正弦波的 5 個（升頻、降取樣率重試、不同取樣率無縫、dsd 核心）只差在各家 `std::sin` 的捨入（約 −283 dBFS 以下）。dsd 核心的位元串流整個不同，因為 sigma-delta 調變器會把輸入的任何差異放大；輸入完全相同時（`modulator-test`）兩個平台逐位元組相同。
- 時間相關的測試（搜尋、暫停、設定變更、即時輸入）讓裝置以 4 倍速（即時輸入為 1 倍速）消耗；音軌長度足以讓背景工作在慢機器上完成。

## 播放器的結構（`core/src/player/`）

`core/src/player.cpp`（約 1800 行）拆成擁有自己狀態的元件，以及依主題分檔實作的處理執行緒：

| 檔案 | 內容 |
|---|---|
| `player.cpp` | 公開 API（`player.h`），只轉給處理執行緒 |
| `common.h` / `.cpp` | 處理區塊大小、`requested_rate`、`same_output`、`chain_settings`、濾波器描述、交叉淡化用的 FIFO（輸出的能力改由 `OutputCaps` 提供，N24） |
| `report.h` / `.cpp`（`Report`） | 給主程式的報告與回呼、事件、設計進度、bit-perfect 與原因、濾波器描述、除錯 JSON、ASIO 取樣率 |
| `timeline.h`（`Timeline`、`Switch`） | 裝置 frame 時間軸、已解碼未聽到的無縫換軌、正在聽的軌與位置 |
| `output_session.h` / `.cpp`（`OutputSession`） | 裝置、環、正在推送的 chunk、裝置維護（驅動訊息、回呼速率、遲到的回呼、重設要求：回傳 Ok / Reopen / Fail，由播放器重開） |
| `change_plan.h` / `.cpp` | 設定變更要不要重開裝置（純函式） |
| `crossfader.h` / `.cpp`（`Crossfader`、`History`、`FadeQuantizer`） | 重建的處理鏈預熱（`Warm`：分輪、在背景執行緒）、依內容延遲對齊、升餘弦交叉淡化；預熱用的輸入歷史；淡化後的 TPDF 重新量化 |
| `join.h`（`Join`） | 不同取樣率無縫換軌的接合狀態：舊鏈的尾巴與新鏈的開頭，由 `join_produce` 逐塊做出 |
| `track_queue.h` / `.cpp`（`TrackQueue`） | 主程式設定的下一軌（有自己的鎖）、背景預備（開檔、需要時建新鏈）、邊界時交接 |
| `core.h`（`Player::Impl`） | 處理執行緒的狀態與方法宣告；`Stream` 介面：PCM 與 DSD 直送的差異 |
| `core.cpp` | 執行緒：開始、**單一**播放迴圈（PCM 與 DSD 直送原本各一份，現在經 `Stream` 共用）、傳輸、裝置維護、結束 |
| `pcm_stream.cpp` | PCM：開裝置與處理鏈、產生 chunk、交叉淡化到重建的處理鏈 |
| `dsd_stream.cpp` | DSD 檔直送、DSD 靜音與串流結尾 |
| `gapless.cpp` | 下一軌：預備、換解碼器、經新的處理鏈接起來、它的增益 |
| `changes.cpp` | 設定變更：就地、背景重建、重開裝置 |
