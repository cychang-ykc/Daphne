# N4 播放整合

`core/include/daphne/engine/chain.h`、`core/src/chain.cpp`、`core/include/daphne/engine/player.h`、`core/src/player.cpp`、`core/src/player/`（結構見 N25）、`capi/`、`cli/main.cpp`

## 處理鏈（`DspChain`）

```
解碼 → 降混（來源聲道 ≠ 裝置聲道）
     → 增益（音量 + headroom）→ 交叉饋送 → EQ          全部在原取樣率
     → pcm 核心：重取樣到裝置取樣率（原取樣率且不 apodize 時不放這一級）
       dsd 核心：同一個濾波器升到 705.6 / 768 kHz → 調變器前限幅；鏈以 PCM 結束，播放器的 DsdEncoder 調變
     → DSD 檔轉 PCM：前瞻限幅（output.dsd_pcm_limiter）
     → pcm 核心、整數裝置：TPDF 量化到裝置字長；處理鏈透明、整數來源放得進裝置時省略（bit-perfect）
```

- 裝置格式（取樣率、聲道、樣本型態）在建鏈之前決定；dsd 核心的「裝置格式」是調變器的 PCM 輸入（float64）。
- `update(s)`：只有增益、交叉饋送、EQ 改變時就地套用（增益漸變、EQ 滑動或交叉淡化）；濾波器、核心、輸出或最終量化級改變時回傳 false，需要新的鏈。
- `content_delay()`：重取樣器核心峰值位置 + 各級延遲，用來對齊兩條鏈的交叉淡化與無縫換軌，也用來丟掉開頭的延遲（見「開始」）。各級以 `Block::content_delay_frames()` 回報（預設是 `latency_frames()`；重取樣器不插入區塊延遲、`latency_frames()` 為 0（N6），改回報核心峰值位置）。
- 各級之間的緩衝區大小取自 `output_format().max_frames`（這一級最多輸出的 frames），處理鏈不需要知道哪一級會改變 frame 數。
- `flush()` 的暫存緩衝區預先配置，不在串流結束時配置記憶體。

## 播放器（`Player`）

一條處理執行緒（`platform::RealtimeScope`：Windows 為 MMCSS「Audio」、1 ms 計時器解析度、關閉 EcoQoS 節流；macOS / Linux 見 N25；都有 FTZ / DAZ）負責解碼、處理、轉換並寫入環形緩衝（N23），裝置回呼只從環裡讀。

裝置與 PCM 解碼器由 `PlayerDeps` 提供（預設為這個平台的輸出與 `open_decoder`；測試給假裝置與合成來源，N25）。播放器只透過 `AudioOutput` 介面使用裝置（N24）。

### 開始

- pcm 核心：要求 `pcm_output_rate`；裝置打不開或開始不了時，以 2 的冪逐次降低取樣率重試（仍須是來源的整數倍）。這些都失敗、而裝置曾經開在鏈用不了的取樣率時（沒有這首歌取樣率家族的 DAC：只有 48 kHz 的裝置播 44.1 kHz，或最高 96 kHz 的 DAC 播 192 kHz），能轉換的輸出（`OutputCaps::converts`：Core Audio 獨佔）最後再試一次來源取樣率、請輸出轉成裝置的取樣率（`OutputRequest::convert`，log「trying 44100 Hz (resampled by the system)」）。所以同家族往下（要 705.6 kHz、DAC 只到 352.8 kHz）一樣由 Daphne 的濾波器升頻，不會被系統轉換；裝置根本打不開（被其他程式 hog、沒有 hog mode）時也不會再試。
- dsd 核心：有原生 DSD 的輸出（ASIO）先試原生 DSD、再試 DoP；裝置拒絕的 DSD 倍率逐次降到 DSD64；`output.max_dsd` 限制起點。共享混音的輸出（`OutputCaps::shared_mix`：WASAPI 共享、Core Audio 共享）無法傳 DSD，直接報錯；輸出回報 `system_rate`（會轉換）時 DoP 也不採用。
- 報告的 `system_rate`：輸出把串流轉成裝置自己的取樣率時（Core Audio 的轉換器、WASAPI 共享的 `AUTOCONVERTPCM`），裝置實際的取樣率；`device.rate` 仍是 Daphne 送出的取樣率。此時不是 bit-perfect，原因「the system resamples to the device's N Hz」（排在 shared mode 之前）。C API 的報告 JSON 也有這個欄位，Mac 與 Windows 的訊號路徑以它顯示實際輸出取樣率、標成重新取樣，並加一列「系統轉換」。
- 開裝置時中間失敗的嘗試（PCM 的取樣率逐級下降、DSD 的原生 → DoP → 較低倍率）各送一個事件「the output at … failed (原因): trying …」，不只回報最後一次的錯誤。
- ASIO：先短暫啟動一次確認驅動真的能串流這個取樣率，才開始設計濾波器。
- 需要設計的濾波器先查快取；沒有時發出「正在設計」事件並回報進度。
- 預填環形緩衝後才啟動裝置；DSD 先送 `output.dsd_lead_in_ms` 的靜音。
- 只播放音樂，不播濾波器的延遲：開始、跳轉、重開裝置時丟掉鏈輸出的前 `content_delay` 個 frame（`skip_out`；`abs_out` 照算，所以位置、無縫與交叉淡化的對齊都不變）。串流真正結束時送 ⌈延遲 / 倍率⌉ 個零，到最後一個輸入樣本出來為止，它之後的餘振不播；輸出長度等於原曲 × 倍率。補零開始後不再接無縫的下一首。（原本開頭先播一段無聲的延遲、結尾只 `flush()`：最後一首少了一個延遲長度的音樂，1M taps 時 6 s 的檔整首都沒播出來。）
- 跳轉時鏈先 `reset()`：跳轉點之後約半個濾波器長度的輸出只用到跳轉點之後的樣本（濾波器前面的歷史是零）。
- 報告：來源、裝置格式、bit-perfect 與否及原因、濾波器描述、作用中的處理級。

### DSD 檔

- 裝置能接受 DSD（ASIO 原生或 DoP）時直送，不經任何處理；否則轉成 PCM（N3）走 PCM 路徑。
- 共享模式（`shared_mix`）不試 DoP，直接轉 PCM：轉成混音器的取樣率（輸出的 `system_rate`，沒有時是它回報的取樣率），能整除 DSD 取樣率時；否則照常 176.4 / 192 kHz，由系統轉換。修正前會先試 DoP，共享輸出接受任何取樣率，DoP 資料被混音器當成 PCM 轉換，聽起來是雜音。
- DoP 一定原樣送到 DAC：DoP 的嘗試從不要求轉換（`OutputRequest::convert`），輸出回報 `system_rate` 時當成裝置鎖在那個取樣率（以它決定 DSD 轉 PCM 的取樣率）。
- 獨佔模式下 DoP 被裝置鎖在較低的取樣率時，若它低於平常的 176.4 / 192 kHz 又能整除 DSD 取樣率，就以它轉 PCM（鏈只會往上升頻，原本固定 176.4 kHz 會整首播不出來）；最高只到 96 kHz 的 DAC 因此也能播 DSD 檔。

### 播放中改設定（`apply`）

| 類型 | 條件 | 做法 |
|---|---|---|
| 就地 | 只有增益 / 交叉饋送 / EQ / headroom 改變 | `DspChain::update`，無縫 |
| 重建 | 濾波器或最終量化級改變 | 新鏈在背景執行緒建立（低於正常優先權，可被更新的設定取消），以最近的輸入預熱（也在背景，見下），依內容延遲對齊，50 ms 升餘弦交叉淡化 |
| 重開裝置 | 核心、輸出取樣率、輸出裝置、調變器設定改變 | 播完已排隊的部分、最後一塊淡出、裝置排空後重開，在目前位置繼續並淡入 |

重建的預熱（最近約 3 秒的輸入通過新鏈）不在處理執行緒上做：長濾波器時它可能比環還長。

- 背景執行緒（低於正常優先權，與處理執行緒相同的 flush-to-zero）以輸入歷史預熱新鏈，目前的處理鏈照常播放。
- 一輪結束時，這段時間解碼的輸入再交給下一輪。只要每一輪比上一輪短（背景比輸入快）就繼續，最多 4 輪。
- 剩下不到一個區塊（4096 frames）時由處理執行緒補完，交叉淡化開始。若輪次不再縮短（處理鏈比輸入慢），也由處理執行緒補完，最多是上一輪的量。
- 若歷史已經不含需要的輸入（高取樣率下一輪太久），就在處理執行緒上從頭預熱，與之前相同。
- 從同一段歷史開始時，分輪預熱與一次預熱的結果逐位元組相同：同一條鏈依序收到相同的輸入，對齊點依開始交叉淡化時目前鏈的位置計算（`tests/test_player.cpp`）。預熱從第一輪開始時的歷史算起，所以新鏈比一次預熱多看到幾輪的輸入，對齊與內容不變。
- 預熱期間的搜尋讓新鏈直接接手（與交叉淡化中搜尋相同）；重開裝置或播放結束則捨棄它。這三種情形都先取消背景的這一輪（`Warm::cancel`，下一個區塊就停），不等它跑完：長濾波器在慢機器上一輪可能要好幾秒，停止或搜尋會卡那麼久。被取消的鏈搜尋時會先 `reset()` 再接手。
- 背景工作（預熱、背景重建）在 `PoolThreadScope` 裡執行，結束時還原浮點控制與一般優先權：MSVC 的 `std::async` 在執行緒池上執行並重複使用執行緒，否則下一個工作（例如濾波器設計）會繼承低於正常的優先權與 flush-to-zero。

同一時間只處理一個變更；處理中的新變更排隊，最新的一個生效。

### 傳輸

- 暫停：裝置繼續運轉（N23），PCM 淡出，DSD 送靜音。
- 搜尋：裝置暫停、清空環（裝置運轉中也安全，N23）、重新預填、繼續。
- 即時輸入（N2）暫停後繼續時會搜尋目前位置：來源暫停期間也一直寫入，解碼器跳回寫入端後方，略過那段積壓（事件「live input: back to the writer」）。即時輸入的環只填到 2 個裝置緩衝（N23），每次讀 10 ms。
- 交叉淡化、淡入、淡出在處理鏈之後改變位準：整數裝置上這些樣本以 TPDF 抖動重新量化到裝置字長（N21）。

### 無縫播放（`set_next`）

- 下一軌在背景執行緒提前開啟；若取樣率不同但能在同一個輸出上播放，連新的處理鏈也提前建好，邊界不用等慢速磁碟或濾波器設計。
- 同取樣率、目前的處理鏈也適用（`DspChain::fits`）：解碼器在邊界直接換成下一軌。
  - 處理鏈依來源而定的部分：取樣率、聲道數、降混時的聲道配置、是否 DSD 轉 PCM，以及要不要最終量化（N21：整數來源放得進裝置字長、且處理鏈透明時才省略）。
  - 所以同取樣率也可能需要新的處理鏈：例如 16-bit 裝置上 16-bit 曲目（bit-perfect，沒有量化級）之後接 24-bit 曲目，需要 TPDF 量化；無損曲目之後接有損曲目也一樣。這時與不同取樣率相同，用提前建好的新鏈接起來。
- 不同取樣率、同一輸出（例如 `output.rate` 為固定值或 `auto`），或同取樣率但需要新的處理鏈：當作一個濾波器接起來。
  - 舊鏈送入 0，帶出前一軌最後的樣本與振鈴。
  - 新鏈處理下一軌開頭，疊加在上面，使下一軌第一個樣本剛好落在前一軌最後一個樣本之後一個來源週期。
  - 新鏈的開頭要涵蓋舊鏈整段尾巴（約兩倍的內容延遲），之後新鏈的輸出才接在後面。以前只處理到新鏈的第一個樣本出來為止：濾波器長時（8192 taps、44.1 → 176.4 kHz），尾巴比這段長約 12500 frames，下一軌在那裡停頓、之後晚這麼多才繼續。
  - 這段接合由處理執行緒一次做一個區塊（`Join`，`join_produce`）：舊鏈的 0 與 flush、新鏈的讀取都只做到下一塊輸出需要的量，與一般播放相同的節奏。以前在邊界一次算完，長濾波器時可能超過環的 0.5 s。輸出與一次算完的相同（`gapless_cross` 的 dump 逐位元組相同）。
  - 接合中不接受新的設定變更與另一個這樣的接合；搜尋或重開裝置時捨棄它。舊鏈在接合聽到之後仍由接合持有，直到它的尾巴做完。
- 每一軌的 headroom（ReplayGain）在它第一個樣本被解碼的位置生效（增益 20 ms 漸變），不是在主程式收到換軌通知時。
- 新的處理鏈在邊界還沒建好（或設定已改變）時不做無縫，這一軌結束，由主程式載入下一軌。
- 換軌在實際聽到時才回報（`on_track_started`）；聽到之前若搜尋或重開裝置，回到原本那一軌與它的增益。
- 報告的 `bit_perfect` 與原因在每次換軌被聽到、就地套用設定、新鏈接手時重新計算（依聽到的那一軌與它的處理鏈），不只在開始時。

### 裝置維護

- 驅動訊息、回呼過快（驅動在背後改了緩衝大小）、遲到的回呼都寫進事件記錄。
- 驅動要求重設時重開裝置並在原位置繼續，10 秒內最多 3 次。
- DoP 串流在停止前補 PCM 靜音，DAC 離開 DSD 模式。

### 處理速度（`realtime_factor`）

- 處理執行緒量測處理鏈與其後的轉換（漸變、裝置格式轉換、DoP / DSD 封裝）花的時間，不含讀檔、等待裝置與無縫換軌的預備；每 2 秒音訊更新一次倍數（音訊秒數 ÷ 處理秒數），放在報告的 `realtime_factor`（C API 的 `report.realtime`、除錯 JSON 的 `rt`）。`dc_state` 的 `report.realtime` 每次讀取時取最新的值（`Player::realtime_factor()`），不是上次開始 / 變更時報告裡的值（那時還沒有量測，是 0）。
- 連續兩個 2 秒區段低於 1.2 倍時發出一次 `info` 事件：裝置會持續 underrun，建議改用較短的濾波器、不用 double-double 摺積或降低輸出取樣率。回到 1.5 倍以上才會再次警告，所以一段持續的慢速只有一則。
- 換處理鏈（開始、需要重開的設定變更、不同處理鏈的無縫換軌、交叉淡化結束）時重新量測：濾波器的冷啟動不算進新鏈的速度。
- 1.2 倍而不是 1 倍：環只有約 0.5 s，排程抖動與其他行程會吃掉剩下的餘裕。

## C API（`capi/daphne_core.h`，`daphne_core.dll` / `libdaphne_core.so` / `.dylib`）

呼叫只有主程式 → 函式庫一個方向；事件與狀態以 JSON（UTF-8）輪詢；錯誤以回傳碼加選用訊息緩衝區表示，例外不會越過邊界（處理執行緒與背景執行緒上的例外也轉成載入失敗或 `failed` 事件，N27）；每個函式都可以從任何執行緒呼叫。

| 函式 | 說明 |
|---|---|
| `dc_abi_version` | 2：有 `*_utf8` 函式（N25）；3：有保留裝置的函式；4：`dc_cancel`、`dc_stop` 能中斷載入（`DC_ERR_CANCELLED`）、`dc_state` 的 `loading` |
| `dc_cancel` | 中斷進行中的 `dc_load`（回傳 `DC_ERR_CANCELLED`）並立刻返回，不停止其他正在播的東西：給停止排在載入後面的宿主（helper） |
| `dc_create` / `dc_destroy` | 建立 / 停止並釋放 |
| `dc_load(path, settings_json, seconds, play)` | 開檔並開始（或暫停）；阻塞到開始或失敗。回傳 `DC_ERR_SETTINGS` / `DC_ERR_FILE` / `DC_ERR_DEVICE`，被 `dc_stop` 或 `dc_cancel` 中斷時 `DC_ERR_CANCELLED`。`path` 為 `wchar_t`（Windows：UTF-16）；`dc_load_utf8` 收 UTF-8 |
| `dc_apply(settings_json)` | 播放中改設定；設定有錯回傳 `DC_ERR_SETTINGS`，套用時內部失敗（記憶體不足等）回傳 `DC_ERR_INTERNAL`（原本一律是 `DC_ERR_ARG`） |
| `dc_pause` / `dc_seek` / `dc_stop` | 傳輸 |
| `dc_set_next(path)` / `dc_set_next_gain(path, headroom_db)` | 無縫的下一軌（與它自己的增益；NaN 表示沿用）；`*_utf8` 版本收 UTF-8 |
| `dc_state(json)` | 狀態（`idle` / `loading` / `playing` / `paused` / `ended` / `failed`）、位置、長度、換軌計數、設計進度、錯誤、報告、ASIO 可用取樣率；不等 `dc_load`，載入中回報 `loading` |
| `dc_poll_event(json)` | `started` / `track` / `changed` / `ended` / `failed` / `info` |
| `dc_design` / `dc_meter` | 設計進度、電平 |
| `dc_filter_cache_dir`（`_utf8`）/ `dc_filter_cache_prune` | 濾波器快取；資料夾回傳 0 表示快取關閉，`DC_ERR_INTERNAL` 表示資料夾算不出來（原本兩者都回傳 0） |
| `dc_devices(json)` | 輸出裝置 |
| `dc_keep_device(on)` / `dc_release_device()` / `dc_device_kept()` | macOS 獨佔：換曲時保留裝置（整個程序；N24「保留裝置」）、放掉保留的裝置（還原後回傳 1）、目前是否保留著 |
| `dc_live_bus(base, cap_frames, rate)` / `dc_live_rate(rate)` | 即時輸入的共用環形緩衝與來源取樣率；`dc_load` 以路徑 `live:` 播放（N2）。`dc_live_bus` 返回之後舊的環就可以釋放，播放中也可以（先取下、等讀取結束，N2「安全卸離」）；換成另一個環也算一次卸離。`base` 為 NULL 時卸離。只能從一條執行緒呼叫 |
| `dc_live_socket(path, rate)` | macOS MIKU 的 Unix socket 來源：保留的接口，尚未實作，一律回傳 0（N26） |

### C API 的執行緒

- `dc_load`、`dc_apply`、`dc_stop`、`dc_destroy` 拿操作鎖 `op`，一次一個。`dc_load` 持有它直到播放開始：第一次設計長濾波器可能要幾分鐘，裝置開得慢（驅動卡住）也會一直等。
- `dc_state`、`dc_meter`、`dc_pause`、`dc_seek`、`dc_set_next*` 不拿 `op`：在一把只保護指標的鎖 `pm` 下複製 `shared_ptr<Player>`，之後透過這份複本呼叫（Player 的公開函式本來就能從任何執行緒呼叫：原子變數或它自己的鎖）。`dc_poll_event`、`dc_design` 原本就不拿。
- 載入中還沒有 player 時，`dc_state` 回報 `loading`（含 `design`）；`dc_pause` / `dc_seek` / `dc_set_next` 沒有作用（`dc_load` 的 `play`、`seconds` 就是開始的狀態，下一首等載入完成再設定）。
- 停止時先取下指標（之後的查詢看不到它），再在持有 `op` 的執行緒上停止；查詢手上若還有複本，等它放開才釋放 player，所以釋放一定在這個執行緒，不會落到查詢的執行緒（例如宿主的 UI 執行緒）。
- 測試：假裝置第一次開啟要 1.5 秒，載入期間每 10 ms 查一輪（state、meter、pause、seek、set_next）：最慢 0.27 ms，狀態都是 `loading`。修正前第一輪就等了 1400 ms。
- `dc_stop`（與 `dc_destroy`）先中斷進行中的載入，再拿 `op`：`dc_load` 從拿到 `op` 起，`dc_stop` 都會記下取消；它啟動的 player 在 `pm` 下公開為 `starting`，`dc_stop` 不等 `op` 就對它呼叫 `stop()`。濾波器設計（`CancelScope`）與預先填環會檢查，開啟流程在每次嘗試前、啟動裝置前也檢查，被取消就不再試下一個取樣率、不啟動裝置。被取消的 `dc_load` 回傳 `DC_ERR_CANCELLED`（−7），不公開 player、什麼都不播；兩個宿主把它當成停止，不顯示錯誤。
- 中斷不了的：在驅動裡卡住的裝置開啟（或關閉上一首的串流）。`dc_stop` 等它結束，之後裝置不會被啟動。宿主因此不在 UI 執行緒上呼叫 `dc_stop`。
- 設計的平行段落（`parallel_for`）把呼叫者的取消旗標交給每個工作執行緒（原本只有呼叫的執行緒會檢查，工作執行緒跑完自己那一段才停：核心少的機器上取消要 4 – 6 秒）；工作執行緒的例外在 join 後由呼叫者丟出；倍頻 FFT 的第一輪每個區塊檢查一次。計算順序不變，結果逐位元相同。
- 已知例外（N26「已知問題」）：取消剛好落在裝置啟動的那一刻（最後一次檢查之後），裝置會先開始，`dc_load` 再停止它並回傳 `DC_ERR_CANCELLED`，事件佇列與報告留著那首的 `started`；取消落在啟動完成之後、公開 player 之前的幾微秒，會被記下卻沒有作用，`dc_load` 回傳 `DC_OK`；`dc_load` 還沒拿到 `op` 之前的 `dc_cancel` 不會被記下。
- 測試：1M taps 設計（2 個設計執行緒）途中 `dc_stop`：46 ms 返回、`DC_ERR_CANCELLED`、裝置沒有收到任何資料（修正前 21.9 秒：等整個設計完、開始播放後才停）。裝置開啟要 1.5 秒時 `dc_stop`：等開啟完成，裝置不啟動。三條執行緒同時反覆載入、停止、查詢：每次載入都是播放或取消，沒有其他結果。
- `dc_destroy` 先中斷進行中的 `dc_load` 並等它返回（拿 `op`），再釋放 player；其他呼叫（輪詢、查詢）不能還在進行，呼叫之後也不能再有呼叫開始（標頭寫明）：宿主先等自己的輪詢執行緒結束。

### Windows 擴充（`src/Daphne.Extension/DaphneEngine.cs`）呼叫 C API 的方式

- 會等的呼叫都不在 MIKU 的執行緒上：`Stop()` 把世代（`_epoch`）加一、立刻更新狀態，`dc_stop` 在背景依序執行（中斷進行中的載入）；`dc_apply` 也在背景依序執行；`dc_load` 原本就在 `Task.Run`。查詢（`dc_state`、`dc_meter`）、`dc_pause`、`dc_seek`、`dc_set_next` 不等，照舊直接呼叫。
- 載入：先等之前發出的停止做完（否則它會取消這次載入），回來時世代變了（中途按了停止）就不算載入完成；成功的話再停一次。`DC_ERR_CANCELLED` 不顯示錯誤。世代在 `LoadAsync` 一進來就記下：停止之前就排隊的載入不會在停止之後才播。
- 換歌（MIKU 的上一首 / 下一首直接呼叫 `LoadAsync`，中間不停止）：每次載入拿一個序號；等前一個載入讓出時，最新的載入每 50 ms 呼叫一次 `dc_cancel`（前一個可能還沒進到 `dc_load`，取消要進去之後才有效），被更新的載入取代的直接跳過，回傳 `DC_ERR_CANCELLED` 不顯示錯誤。原本新的載入排在前一個後面，第一次設計長濾波器時連按幾次換歌，每一首都會依序設計完。`dc_cancel` 只設旗標、立刻返回，而且在這次載入進入之前呼叫，不會取消到自己。
- `Dispose()`：停止在背景執行，等輪詢執行緒（2 秒）與進行中的停止、載入、設定（5 秒）都結束才 `dc_destroy`；等不到（驅動卡住、呼叫還在核心裡）就不釋放 player，避免在呼叫進行中釋放（程式正在結束）。原本只等輪詢執行緒 0.5 秒就 `dc_destroy`。
- 事件（`TrackStarted`、`Ended`、`Failed`、`Changed`）照舊從輪詢執行緒觸發：MIKU 自己的內核也是如此，MIKU 端加鎖並轉到 UI 執行緒（`Post` / `BeginInvoke`），所以不使用建構子的 `ui` 參數。
- 驗證（主控台程式驅動 `DaphneEngine`，VB-Audio Hi-Fi Cable，1M taps、2 個設計執行緒）：設計中 `Stop()` 0.7 ms 返回、載入 61 ms 後取消、沒有 `Failed`；正常播放後 `Stop()` 立即返回、`Dispose()` 19 ms；設計中 `Dispose()` 58 ms；`Stop()` 後立刻載入下一首：照常播放（停止沒有取消它）。設計中換歌兩次（1.5 s 後第 2 首、再 0.3 s 後第 3 首）：第 1、2 首在最後一次換歌後 1 ms 內結束，第 3 首 158.7 s 後播放，是它自己一次設計的時間（期間穩定用滿 2 個核心）；原本要依序設計三首。
- MIKU 關閉時在 UI 執行緒上同步呼叫 `Dispose()`，所以取消要多久，視窗就卡多久。設計裡沒有檢查取消的段落（double-double FFT 的位元反轉與 twiddle 表、最小相位的單執行緒迴圈；1M taps × 8 時 FFT 有 2^26 點）原本在 16 個設計執行緒時約佔設計開始後的第 3 – 9 s，期間停止、換歌、關閉都要等它跑完：MIKU 設計中關閉，視窗約 5 s 才消失。這幾段加上檢查後（設計結果逐位元相同），在設計中每 3 s 關閉一次（16 個執行緒，3 – 45 s）都在 107 – 658 ms 內結束，2 個執行緒（10 – 150 s）41 – 575 ms。

## helper 程序（`helper/main.cpp`，`daphne-helper`）

給不是原生程式的主程式用（macOS 的 MIKU 是 Electron）：播放器跑在子程序裡，stdin / stdout 每行一個 JSON 物件（UTF-8），底下就是上面的 C API，一個指令一次呼叫，所以主程式的行為與 Windows 擴充經 P/Invoke 呼叫時相同。子程序掛掉不會拖垮主程式；主程式結束（stdin 讀到結尾）時 helper 停止播放、放開裝置再結束。

| 請求（`{"id": n, "cmd": ...}`） | 回應（`{"id": n, "ok": ...}`） |
|---|---|
| `hello` | `version`、`abi` |
| `load`：`path`（UTF-8）、`settings`（物件或字串）、`seek`、`play` | `code`、`error`（阻塞到開始或失敗） |
| `apply`：`settings` | `code`、`error` |
| `pause`：`paused`；`seek`：`seconds`；`next`：`path`、`gain`（dB 或 null）；`stop`：`hold` | — |
| `state` | `state`（`dc_state` 的物件）、`kept`（保留著裝置、沒有載入） |
| `meter` | `l`、`r` |
| `devices` | `devices`（`dc_devices` 的物件） |
| `cache_dir`；`cache_prune`：`settings`、`limit_mb` | `dir`；`bytes` |
| `quit` | 停止播放、回應後結束 |

- 主動送出（沒有 `id`）：`{"e": "hello", ...}`（啟動時一次）、`{"e": "event", "event": {...}}`（`dc_poll_event`，每 20 ms 檢查）、`{"e": "design", "progress": x}`（濾波器設計進度改變時）。
- 指令依序在一條執行緒上執行（設計長濾波器時 `load` 可能要幾分鐘）；`state`、`meter`、`devices`、`cache_dir`、`hello` 由讀取的執行緒立刻回答，不排在 `load` 後面，也不等 `dc_load`（C API 的查詢不拿操作鎖，見上方「C API 的執行緒」）。`quit` 也由讀取的執行緒處理：停止讀取、丟掉還沒開始的指令、停止播放、等目前的指令結束才回應（在 Windows 上，從別的執行緒關掉 stdin 打斷不了阻塞中的讀取）。
- `stop` 也先由讀取的執行緒處理，再照順序排進佇列：還在排隊的 `load` 直接丟掉（各自回覆 `code` −7），正在執行的 `load` 以 `dc_cancel` 中斷（不等它，回覆 −7）。停止因此不會排在載入後面：修正前，第一次設計 1M taps 時按停止，要等設計完、這首開始播、排隊的下一首也載入並開始播，35.7 秒後才停；現在 44 ms，什麼都沒播（`verify` 以外的腳本測試：Windows、VB-Audio Hi-Fi Cable）。engine.js 的 `stop()` 原本就把載入世代加一，晚到的載入回覆不會被當成載入完成。
- `load` 也一樣（macOS MIKU 換歌只送 `load`，中間沒有 `stop`）：之前的載入被取消或丟掉，新的照順序排進佇列。每個 `stop` / `load` 把世代加一，排隊的 `load` 帶著自己的世代；worker 已經取出、還沒開始的 `load` 看到世代變了就不執行（回覆 −7）。剩下的空檔只有比對世代到 `dc_load` 開始之間的幾微秒。修正前，第一次設計 1M taps 時連換兩首，前兩首都設計完並開始播，最後一首 20.6 s 後才播（Windows、16 個設計執行緒；Mac 的 4 核心測試機一次設計要約 160 s）；現在前兩首立刻回覆 −7，最後一首 0.13 s 後播放。engine.js 的 `load()` 也有載入世代，被取代的回覆直接忽略。
- helper 啟動時打開 `dc_keep_device`（與 MIKU 自己的 Core Audio 輸出相同）：macOS 獨佔模式下，播完、`stop` 帶 `hold`、下一次 `load` 之前，裝置都保留著（hog、取樣率、DAC 格式，IO 送靜音），下一次 `load` 同一台裝置時直接接手。`stop` 不帶 `hold` 放開裝置（還原取樣率與 DAC 格式、放掉 hog，N24）：MIKU 播 YouTube Music、離開 MIKU 且沒在播時要的「讓出裝置」就是它；`quit` 與 stdin 結束也會放開。
- macOS MIKU 的模組（`miku/`）以 helper 實作 MIKU 的播放核心：`extension.js`（模組、頁面的 RPC：`state`、`set`、`openCache`、`clearCache`、`bitPerfect`）、`engine.js`（MIKU 的 `AudioEngine` 驅動的 backend：載入、傳輸、無縫、保留與讓出裝置（`stop({ release })`、`release()`、`holdsDevice`，與 MIKU 的 `native-audio.js` 相同）、裝置列表）、`settings-map.js`（MIKU 的設定 → Daphne 的設定）、`signal.js`（播放路徑卡片）、`helper-client.js`；頁面檔案與 Windows 擴充相同（`miku/web` 是指向 `src/Daphne.Extension/web` 的 symlink）。`verify/miku_shell.js` 以替身 host 驅動它（N26 步驟 7d）。
- 看不懂的一行（不是 JSON 物件）只寫到 stderr，不回應，即使裡面有 `id`：等回應的主程式要有逾時。
- helper 忽略 `SIGPIPE`：主程式先結束、stdout 的另一端關閉時，寫出只會失敗，helper 照樣在 stdin 讀到結尾時走 `quit` 的清理。原本下一次寫出（事件、設計進度、回覆）就被系統結束（Linux 上結束碼 141），取樣率與 DAC 格式不還原。Windows 沒有這個訊號，寫到已關閉的 pipe 本來就只是失敗。只關掉 stdout、stdin 仍開著時，helper 繼續執行到 stdin 結束為止（MIKU 當掉時兩條一起關）。ctest `helper_closed_stdout`（macOS / Linux）。
- 驗證：`verify/helper.py <daphne-helper> [settings]`（兩個 −60 dBFS 的短檔：暫停載入、無縫的下一軌、事件順序、stop 之後 idle 且沒有裝置被 hog、找不到檔案為 −3、未知指令、quit）。Windows（Hi-Fi Cable）與 macOS 11（內建輸出，Core Audio 獨佔）全部通過。

## CLI

```
daphne devices [--probe]
daphne play [--settings file] [--device id|index] [--shared|--exclusive|--asio [driver]]
            [--start S] [--length S] [--next file] [--watch] [--script t:cmd,...] files...
daphne render-dsp <in> <out.wav> [--settings file] [--channels N] [--bits 16|24|32] [--float]
```

- `--watch`：設定檔一改就套用（測試就地 / 重建 / 重開）。
- `--script "1.5:pause,2.5:resume,3.5:seek=1"`：依時間執行傳輸指令。
- `render-dsp`：整條處理鏈離線輸出成 WAV（虛擬裝置：`--bits` 整數位元深度，預設 24；`--float` 為 float32）；dsd 核心輸出播放器實際送出的 DoP 串流。
- 播放時的裝置位元深度不是設定項：WASAPI 獨占由寬到窄協商（int32 → 24-in-32 → float32 → packed24 → int16），ASIO 用驅動指定的樣本型態（N24）。
