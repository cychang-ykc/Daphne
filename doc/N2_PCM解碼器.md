# N2 PCM 解碼器

## WAV / AIFF / AIFC（`decoder_wav.cpp`，dr_wav）

| 來源 | 讀法 | 精度 |
|---|---|---|
| 整數 PCM 8–32 bit、A-law、μ-law、ADPCM | `drwav_read_pcm_frames_s32`（左對齊 s32）× 2^-31 | 精確 |
| float32 | `drwav_read_pcm_frames_f32` → double | 精確 |
| float64 | `drwav_read_pcm_frames`（原生位元組序）**直接讀進輸出緩衝區** | 位元相同 |

- float64 不走 dr_wav 的 f32 路徑（會被捨入成單精度）。`drwav_read_pcm_frames` 依容器把大端（AIFF）樣本轉成原生位元組序；不可用 `_le` 版本，它只回傳原始位元組，大端 AIFF 的 float64 會變成亂碼。
- 效能：float64 沒有中間緩衝區與複製；整數與 float32 使用重複利用的成員緩衝區，不在每次 `read` 配置。
- `channel_mask` 取自 WAVE_FORMAT_EXTENSIBLE，供多聲道降混使用。
- 只有 `DR_WAVE_FORMAT_PCM` 標記 `lossless_int` 與 `bits`；壓縮格式（A-law 等）與浮點視為非整數來源。

## FLAC（`decoder_flac.cpp`，dr_flac）

- `drflac_read_pcm_frames_s32` × 2^-31，所有位元深度（含 32 bit）精確。
- 停用 Ogg FLAC（`DR_FLAC_NO_OGG`）：OGA 交給 FFmpeg。
- 搜尋使用 dr_flac 的 seek table / 二分搜尋，落點為精確樣本。
- dr_flac 照抄 STREAMINFO，取樣率 0 也能開啟；`open_decoder` 對所有解碼器（含退回的 FFmpeg）統一拒絕取樣率或聲道數 ≤ 0 的檔案，否則播放器以取樣率做的除法會讓整個程序結束（N27）。

## MP3 / MP2 / MP1（`decoder_mp3.cpp`，minimp3_ex）

- 浮點輸出（`MINIMP3_FLOAT_OUTPUT`）：保留完整精度，超過 0 dBFS 的樣本不被截斷（不採用 int16 輸出）。
- minimp3_ex 讀取 LAME / Info 標籤，裁掉編碼器延遲與尾端補零，達成無縫。
- `MP3D_SEEK_TO_SAMPLE`：精確到樣本的搜尋。
- 從預讀開啟（`mp3dec_ex_open_cb`）失敗時要自己 `mp3dec_ex_close`：minimp3 不會釋放它已配置的 128 KiB 讀取緩衝區（檔案版本會）。每個開不了的 MP3 原本都漏掉這塊記憶體（CI 的 fuzz 工作以 LSan 抓到）。

## FFmpeg（`decoder_ffmpeg.cpp`，`DAPHNE_HAVE_FFMPEG`）

- avformat → 最佳音訊串流 → avcodec → swresample 轉為交錯 float64，取樣率與聲道配置維持來源。
- 無損整數編碼（ALAC、APE、WavPack、TTA、其他容器內的 FLAC、PCM）在 float64 中精確，標記 `lossless_int`。
- **MP4 無縫**：FFmpeg 已去掉編碼器延遲；尾端補零依 iTunSMPB 標籤的長度裁切，沒有標籤時使用串流長度（edit list）。位置從串流起始時間算起，frame 0 即第一個可聽樣本。Ogg（Vorbis / Opus）與 MP3 的裁切由 FFmpeg 處理。
- **搜尋**：有損編碼的每一框依賴前一框（MDCT 重疊），因此提前 4096 frames 起解，等解碼器穩定後再丟棄目標之前的樣本；靠近開頭時直接從頭解，以免跳過解碼器需要的延遲封包。
- 沒有 FFmpeg 時改由 stub 回傳「未啟用」錯誤，其他格式不受影響。

## 預讀（`file_bytes.cpp`，`file_bytes.h`）

WAV / AIFF、FLAC、MP3 與 FFmpeg 的解碼器不直接讀檔，改讀 `FileBytes`：背景執行緒把檔案預先讀進一個固定大小的視窗，解碼器（在處理執行緒上）讀記憶體。原因：外接 USB 硬碟停止回應約 3 秒時，裝置播出斷音。解碼器原本在處理執行緒上讀檔，而沒有濾波器時環只有 0.5 秒。

- **視窗**：64 MiB（`kWindow`），或比它小的整個檔案。存的是解碼器讀取位置前方的資料，以環形緩衝存放（檔案位置 o 在 `o % 容量`）。背景執行緒以磁碟的速度把它補滿，遠遠領先播放，所以比視窗的播放時間短的停頓聽不到：64 MiB 約是 16-bit / 44.1 kHz WAV 的 6 分鐘、24-bit / 192 kHz 的 1 分鐘。記憶體與檔案大小無關，超過 1 GiB 的檔案一樣預讀（PR #54 原本整檔讀進記憶體，上限 1 GiB，更大的檔不預讀）。
- **讀取位置後方**保留 1 MiB（視窗很小時是容量的 1/4），給解碼器往回的小幅 seek；整個放得進視窗的檔案不丟資料，往回 seek 也讀記憶體。
- **移動視窗**：讀取的位置在視窗後方，或超過視窗前緣一次磁碟讀取（2 MiB）以上時（seek、FFmpeg 到 M4A 尾端讀索引），視窗移到那裡，只等那個位置的一次磁碟讀取（移動後第一次只讀 256 KiB），不必等背景執行緒依序讀過中間的資料。移動前已在進行的那次讀取，結果丟掉（世代編號）。
- 解碼器只在背景執行緒還沒讀到的地方等待：檔案的第一次讀取、移動後的第一次、或追上停住的磁碟時。`read` 一定回傳要求的全部位元組，除非到了檔尾或磁碟讀取失敗。dr_libs 與 minimp3 把短讀當成檔尾，所以不能回傳部分資料。
- 檔案在播放中被截短：讀到新的檔尾就回傳已有的部分（短讀），不會卡住。
- 關閉不等背景執行緒：卡在磁碟裡的讀取不會卡住呼叫者，執行緒讀完那一次後自己結束。Windows 以共享讀、寫、刪除開檔，播放中的檔案仍可改名或刪除。
- 開不了檔、空檔、配置不到視窗時回傳 nullptr，解碼器照舊直接讀檔。
- 播放迴圈的 log：一圈超過 250 ms 時記下時間花在哪（解碼、poll、push、upkeep；設定與 transport 另列），以及當時環裡有多少、underrun 次數；預讀的一次磁碟讀取超過 500 ms 時記「read ahead: a disk read of … took … ms」。

## 即時輸入（`decoder_live.cpp`，`live_source.h`）

主程式與一個它無法控制的音訊來源（YouTube Music 網頁的 Web Audio 擷取）共用的環形緩衝，以路徑 `live:` 當成解碼器開啟。

- 版面（`dc_live_bus`）：uint32 寫入位置（frame，會繞回）｜12 位元組保留｜float32 立體聲。來源先寫樣本、再寫位置，位置要以 release（或循序一致）的原子寫入發布：解碼器以 acquire 讀取位置，之前的樣本才保證看得到（x86 上一般的寫入就有這個順序，ARM64 上不一定）。
- 容量至少要大於「目標（最多 0.30 秒）× 取樣率 + min(4096, cap / 2)」：否則持有目標之前就先被判斷為「被追過」，一直重新同步、只輸出靜音（192 kHz 的來源要大於約 61700 frames）。MIKU 的 96000 frames 在 48 kHz 下足夠。
- 卸離：`set_live_bus(nullptr)`（或換上另一個環）在解碼器已經沒有讀取留在舊環裡時才返回，主程式之後就能釋放那塊記憶體，播放中也可以（之後讀到靜音，直到再給一個環）。解碼器只在 `produce()` 裡碰環，期間持有租約（讀取計數）；換環時先清掉指標、等計數歸零，再設定新的容量與指標，所以不會拿到新指標配舊容量。
  - `set_live_bus` 沒有自己的鎖，只能從一條執行緒呼叫（兩條同時換環時，可能留下一個環的指標配另一個環的容量）。
  - 播放中卸離時，解碼器 20 ms 後把它當成一次斷流：目標加 50 ms，而且這個值是學到的、在程式執行期間都保留（見下）；重新給環之後要 60 秒以上沒有斷流才開始降回。
  - 換上另一個環時，解碼器沿用舊環的讀取位置，只有新環的寫入位置落在讀取位置後面或超過一整圈時才重新同步。新環的寫入位置若在讀取位置前方、又不到一整圈，解碼器會把新環裡讀取位置之後、從沒寫過的部分當成音訊讀出（N26「已知問題」）；主程式換環時應該讓寫入位置從 0 重新開始。
- macOS MIKU 的 Unix socket 來源（`live_connect`、`dc_live_socket`）只保留接口、尚未實作（N26）。
- 來源有自己的時鐘，而且是一陣一陣送：在環形緩衝裡保持約 0.15 秒的抖動緩衝，以讀取速率的微調（最多 ±0.5%，平滑後實際遠小於 0.3%）維持在那裡，用 4 點 Hermite 內插。不丟也不重複樣本，所以沒有爆音。
  - 0.15 秒依實測：MIKU 的 YouTube Music 頁面每 40 或 60 ms 送一個 2048 frame 的區塊（AudioWorklet），90 秒內最多落後平均進度 109 ms；0.15 秒涵蓋它、每次 10 ms 的讀取與一點餘裕。原本是 0.3 秒。
  - 目標會依來源調整：頁面忙碌時偶爾停頓更久（實測 304 ms，緩衝見底一次）。每次斷流（一整段停頓算一次，不是每回傳一次靜音就算）目標加 50 ms，最多 0.3 秒；連續 60 秒的音訊沒有斷流就減 25 ms，之後每 30 秒再減一次，回到 0.15 秒為止。依讀到的音訊長度計算，不看時鐘。`live_stats().target`、`dc_state` 的 `live.target` 是目前的值。
  - 學到的目標在程式執行期間都保留：下一次即時輸入（例如再開始播 YouTube Music）從上次的值開始，不會每次從 0.15 秒重新撞一次（與 MIKU 自己內核的即時輸入相同）。`live_forget()` 回到最小值（測試用）。
  - 斷流後先靜音，等解碼器重新持有（調高後的）目標才繼續，超過的部分略過：一次空白，而不是一連串 5 ms 的靜音夾著零碎的聲音。
  - 開始時與斷流後，讀取位置停在寫入端後方「目標」處；seek 時停在「目標 + 播放器補環一次取走的量」（`set_live_reserve`：環的上限加一次讀取，播放器開啟即時輸入時設定）。兩者都讓環補滿之後解碼器正好持有目前的目標，多出來的部分（來源一開始的一陣、暫停期間寫入的）直接略過。原本開始時若來源一次送來一大段，會晚約 0.3 秒、由速率微調花一分多鐘追回，而 seek 後環補滿會讓解碼器只剩約 0.03 秒。
  - 開始時與斷流後不加補環的量：解碼器在持有目標之前立刻回傳靜音，播放器的環早已被這些靜音填滿，之後每次只取一次讀取的量；加上的話會一直多留在解碼器裡（MIKU 的 50 ms 緩衝時開始時約 0.26 秒而不是 0.15 秒，速率微調要一分多鐘才追回）。只有 seek 會清空播放器的環、一次補滿。
  - 播放器暫停後繼續時，即時輸入會 seek：讀取位置跳回寫入端後方，略過暫停期間寫入的部分（來源不會停，頁面暫停時也一直寫入靜音）。原本會一直晚那麼久，速率微調要好幾分鐘才追得回來；實測一次 0.5 秒的短暫停讓延遲從約 0.5 秒變成約 1 秒。跳轉在裝置已靜音、環重新填好、淡入之前完成，所以沒有爆音。
- 被寫入端追過、頁面重新載入，或累積超過 1.2 秒（其他原因的停頓）時，從靠近寫入端的位置重新開始。
  - 位置以 2³² 為模數比較（寫入索引是 uint32，44.1 kHz 約 27 小時回繞一次）：回繞不會被當成頁面重新載入。追過的判斷用有號數（環小於 4096 frames 時，原本的無號數相減會回繞，永遠判斷不出被追過）。
  - 兩端都把索引 i 的 frame 放在 i % cap。容量不是 2 的次方時仍然正確，但回繞那一刻環只剩 2³² % cap 個 frames（MIKU 的 96000：23296，48 kHz 約 0.49 秒，平常大於抖動緩衝的 0.15 – 0.30 秒）。但「被追過」的判斷仍以整個容量計算：回繞那一刻若積壓超過這 0.49 秒（例如 seek 時目標 + 補環的量較大，或積壓接近 1.2 秒），會讀到已被覆寫的部分而不重新同步，約 27 小時一次、一個雜音。
- 還沒有持有目標時立刻回傳靜音（播放器預填環形緩衝）；開始之後等來源最多 20 ms，仍然沒有就回傳 5 ms 靜音（計為 starve，目標調高），之後立刻回傳靜音直到再持有目標，播放器不會被卡住。
- 輸出：開啟時來源的取樣率、2 聲道、長度未知（frames = −1）。串流沒有地方可以搜尋：`seek` 改位置計數，並讓讀取位置跳回寫入端後方（見上）。
- 播放器對即時輸入每次只讀 10 ms，環只填到裝置緩衝的 2 倍、至少 50 ms（N23），不是檔案播放的 0.5 秒環加一個 4096 frame 的區塊（約 0.77 秒）。從來源到 DAC 約為 0.15 秒抖動緩衝 + 環（2 × 裝置緩衝）+ 濾波器延遲 + 裝置緩衝；MIKU 的緩衝大小 50 ms、不升頻時約 0.3 秒（原本約 0.5 秒）。
- `dc_state` 在播放即時輸入時有 `live`：環形緩衝裡的秒數、已讀秒數、重新同步與 starve 次數、速率修正、目前的目標。從來源到 DAC 的延遲 = `fill + read − position + latency_ms / 1000`。
